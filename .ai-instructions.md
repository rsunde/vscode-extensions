# AI Instructions for VS Code Extensions Repository

## Repository Context

This repository is a collection of Visual Studio Code extensions managed in a single location. The user relies on AI assistance to create, maintain, and document these extensions efficiently.

## Core Responsibilities

### 1. Documentation Management

**Root README.md**
- ALWAYS update the "Extensions" section when adding or removing extensions
- Follow the format: `- **[Extension Name](./extension-folder-name/)** - Brief description`
- Keep the overview and purpose sections accurate as the repository evolves
- Update any relevant sections when the user's needs or ideas change

**Extension-Specific READMEs**
- Each extension MUST have its own README.md
- Include: purpose, features, usage instructions, configuration, and development setup
- Document any shared configurations used by the extension
- Keep documentation synchronized with code changes

### 2. Extension Structure

Each extension should:
- Be fully self-contained in its own folder
- Follow standard VS Code extension structure
- Include all necessary files: package.json, tsconfig.json, etc.
- Have proper TypeScript/JavaScript source organization
- Include appropriate .vscodeignore file

### 3. Shared Resources

**Configuration Files**
- Identify opportunities to share configurations (ESLint, TypeScript, etc.)
- Document shared configurations in both root and extension READMEs
- Create a `shared/` folder if multiple extensions use common files
- Update shared configs carefully as they affect multiple extensions

**Dependencies**
- Note when extensions share similar dependencies
- Suggest opportunities for consistency
- Document any version constraints or compatibility requirements

### 4. PowerShell Automation

When automation is needed:
- Create PowerShell scripts in a `scripts/` folder
- Name scripts clearly: `new-extension.ps1`, `build-all.ps1`, etc.
- Include comments and documentation in scripts
- Make scripts work from repository root
- Support common parameters and error handling

Example scripts to consider:
```powershell
# scripts/new-extension.ps1 - Scaffold new extension
# scripts/build-all.ps1 - Build all extensions
# scripts/test-all.ps1 - Run tests for all extensions
# scripts/publish-extension.ps1 - Publish specific extension
```

### 5. Responding to User Updates

When the user updates their ideas or needs:
- Update this .ai-instructions.md file to reflect new guidelines
- Update the root README.md to reflect new purposes or structures
- Update affected extensions and their documentation
- Suggest improvements or automations that align with new goals
- Ask clarifying questions if requirements are unclear

## Extension Creation Workflow

When creating a new extension:

1. **Planning**
   - Understand the extension's purpose and features
   - Check for similar existing extensions
   - Identify shared configurations that can be reused

2. **Scaffolding**
   - Create extension folder with kebab-case name
   - Use `yo code` or generate standard VS Code extension structure
   - Set up TypeScript/JavaScript configuration
   - Include proper package.json with all metadata

3. **Documentation**
   - Create extension README.md with comprehensive details
   - Update root README.md Extensions section
   - Document any shared configurations used
   - Add usage examples and screenshots if applicable

4. **Code Implementation**
   - Follow VS Code extension best practices
   - Use TypeScript for type safety when possible
   - Implement proper activation events
   - Add error handling and user feedback

5. **Testing**
   - Include test setup if appropriate
   - Verify extension works in VS Code
   - Test on different scenarios

6. **Finalization**
   - Update all documentation
   - Verify .vscodeignore excludes unnecessary files
   - Ensure package.json is complete
   - Check that extension follows repository conventions

## Code Style and Conventions

### General
- Use TypeScript where possible for better maintainability
- Follow VS Code extension API best practices
- Use clear, descriptive names for commands and settings
- Implement proper error handling and user notifications

### File Organization
```
extension-name/
├── src/
│   ├── extension.ts       # Entry point
│   ├── commands/          # Command implementations
│   ├── providers/         # Language providers, etc.
│   └── utils/             # Utility functions
├── test/                  # Tests
├── resources/             # Icons, snippets, etc.
├── package.json           # Extension manifest
├── tsconfig.json          # TypeScript config
├── README.md              # Extension documentation
└── .vscodeignore          # Files to exclude from package
```

### Naming Conventions
- Folders: kebab-case (e.g., `my-extension`)
- Commands: extension-name.command-name (e.g., `myExt.doSomething`)
- Configuration: extension-name.setting (e.g., `myExt.enabled`)
